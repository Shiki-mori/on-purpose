## 1. 使用场景

**原文。** 日常使用网页版哔哩哔哩（[https://www.bilibili.com/](https://www.bilibili.com/)），主要目的包括：

- 看学习视频
- 看游戏攻略
- 追番
- 看健身视频
- 看生活经验
- 查看关注up更新情况

**补充。** 这些目的都有明确起点：打开网站时心里已经有一件要做的事。网站同时提供推荐流和短视频，浏览过程中很容易从原来的目的滑到无目的滑动。本项目要处理的是这种偏离，而不是减少对哔哩哔哩本身的正常使用。

预设目的只作为个人起步时的例子。目的列表需要能由使用者自己增删，以适应以后出现的新用途。

## 2. 要解决的问题

**原文。** 使用过程中，大量时间花在刷无意义的短视频上。希望限制这种行为。

**补充。** 问题可以拆成两段：

1. **开始时目的不落地。** 打开网站时目的是模糊的，或者打开之后立刻进入推荐流，原本的目的没有被记下来。
2. **使用中途失去察觉。** 看完目标内容之后继续滑短视频，过了很久才意识到时间已经花掉。

因此，干预放在两个时点：进入网站时先声明本次目的；连续使用达到设定时长后再打断一次，问当前实际在做什么。两次询问都留下记录，供以后复盘「当时打算做什么」和「后来实际在做什么」。

当前设想是提醒和记录，让使用者自己决定是否继续。它不屏蔽栏目、不删除推荐、不替使用者判断某条视频是否「无意义」。

## 3. 期望结果

用下来之后，希望达到这些结果：

- 每次有意识地打开哔哩哔哩时，都留下一条本次目的，需要时可以写备注。
- 使用超过自己设定的时长后，会被打断并回答「现在在做什么」，避免长时间无察觉地刷短视频。
- 目的、备注、打断时的回答都能在事后查看，用来对照计划与实际行为。
- 打断可以被暂时关掉，关闭时长由自己设定；主要页面上能随时找到关闭入口，避免为了关提醒而中断正在看的内容太久。
- 规则只作用于自己的 Chrome，不依赖账号体系，也不发布到插件或脚本市场。



## 4. 干预方式



### 4.1 打开时询问本次目的

- 首次打开哔哩哔哩网页（主链接 [https://www.bilibili.com/](https://www.bilibili.com/)）时弹出窗口，询问本次使用目的。
- 询问时提供选项。也可直接跳过。提供直接跳过的按钮。
- 每个选项可输入备注。
- 保存每一次选择和备注，之后可以复盘查看。跳过也需要被记录。
- 目的支持使用者自定义添加。

**补充。** 这条能力可以理解为一次「本次使用声明」：


| 要素      | 说明                                                                                                                  |
| ------- | ------------------------------------------------------------------------------------------------------------------- |
| 触发页面    | 原文写的是主页链接。从视频页、搜索页等其他地址直接进入时是否也要询问，需求文档里再定。                                                                         |
| 「首次」的范围 | 原文写了「首次打开」，但没有定义一次使用从何时开始、到何时结束。候选口径包括：浏览器本次启动、自然日、距离上次询问超过若干小时、以及关闭全部哔哩哔哩标签页之后再次打开。需求文档里选定一种或多种，并写清刷新、多标签页是否会重复弹出。 |
| 选项      | 提供可选目的以及“其他”项。初始可以放入第 1 节里的几类个人常用目的，并允许以后自己添加、对这些目的编辑。                                                              |
| 备注      | 挂在当次选择上，用来写下更具体的内容，例如「线性代数第三章」或「某一季某一集」。备注不是必填项。                                                                    |
| 记录      | 每次确认都保存目的、备注和时间。复盘时能按时间回看这些记录。                                                                                      |
| 未完成询问   | 关掉窗口、刷新或切走时如何处理（视为未声明、稍后再问，或阻止继续浏览），需求文档里再定。                                                                        |




### 4.2 使用达到设定时长后打断

**原文。**

- 使用哔哩哔哩达到一定时间后弹出窗口，打断当前浏览，询问现在在做什么。
- 询问窗口仍然提供选项列表，可写备注。该选项列表与目的选项列表独立，不复用目的选项。
- 时长由使用者设置，单位为分钟。
- 该功能可以在一段时间内关闭，这段时间的长度也由使用者自定义。
- 需要方便的关闭入口，在哔哩哔哩的主要页面随时可关，包括视频播放页、搜索推荐页、主页等。

**补充。**


| 要素       | 说明                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------- |
| 计时对象     | 使用时长：所有哔哩哔哩标签页共用同一计时。页面在后台、视频停止播放、电脑休眠时持续计时。关闭浏览器、关闭哔哩哔哩全部标签页后重置计时，下次打开时从零开始计时。                                |
| 打断内容     | 询问现在正在做什么，提供选项以及“其他”选项，可填写备注。提供“关闭当前标签页“选项，点击后将关闭当前标签页，并将这一行为记录。不复用第 4.1 节的目的选项。备注不是必填项。是否和开站时的目的对照展示，需求文档里再定。 |
| 打断之后     | 回答会写入记录。”关闭标签页“行为也写入记录。该行为仅针对点击提供的关闭按钮，不记录用户在浏览器中自行关闭标签页。回答后重新开始从零计时，可设置指定时间后再次询问。                             |
| 暂时关闭     | 关闭的是「到时打断」，不是删掉历史记录。关闭时长由使用者设定。关闭期间不再弹出时长询问；到期后恢复并立即弹出打断窗口。关闭期间可选择延期。                                          |
| 关闭入口     | 视频播放页、搜索推荐页、主页以及其他主要页面都能找到，不要求先回到某一个固定页面。入口要容易发现，同时不遮挡正常的播放和浏览。                                                |
| 与目的询问的关系 | 两条能力独立：暂时关闭时长打断时，打开网站时的目的询问仍然可以按自己的规则出现。                                                                       |




## 5. 记录与复盘

**原文。** 保存每一次选择和备注，之后可以复盘查看。时长打断时的回答同样属于需要留下的记录。

**补充。** 复盘至少要能看到：

- 时间
- 记录来自「打开时的目的」还是「使用中的打断」
- 选择的目的或填写的回答
- 备注（如果当时写了）

记录保存在本机，供个人查看。导出、统计图表、按目的汇总时长等都不在当前背景范围内，若以后需要，再作为单独需求加入。

## 6. 运行环境与实现取向

**原文。**

- 使用 Chrome。
- 在浏览器插件、篡改猴（Tampermonkey）脚本或其他方式之间比较，选择最合适的一种。
- 仅供个人使用，不上传到插件或脚本市场。

**补充。** 比较实现方式时，用下面这些条件衡量，而不是先假定某一种形态：

- 能在哔哩哔哩页面上弹出询问，并在主要页面提供关闭入口。
- 能把目的、备注、回答和使用者设置持久保存在本机。
- 可实现自定义点击按钮后关闭当前标签页。
- 计时和暂时关闭在刷新、关闭标签页、重启浏览器之后仍然符合需求里写明的规则。
- 个人安装和维护成本可接受，不依赖商店审核或公开分发。
- 站点规则（哪些网址生效、时长、目的列表）集中在可修改的代码或配置中，便于以后加到其他网站。

**选定。** 使用在 Chrome 中以开发者模式加载的扩展（Manifest V3）。不打包上传到 Chrome 网上应用店。安装时在 `chrome://extensions` 打开开发者模式，加载本机的扩展目录；改完代码后在该页重新加载。

比较过三类做法：Chrome 扩展、篡改猴脚本，以及不注入页面的其他做法（书签脚本、本地代理）。选定扩展，是因为它能同时满足第 4.2 节的计时规则，以及「自定义按钮关闭当前标签页」。

### 计时规则与扩展的对应关系

第 4.2 节要求全部哔哩哔哩标签页共用一个计时，并且同时满足：

- 刷新页面后计时继续。
- 只关闭其中一部分标签页后计时继续。
- 页面在后台、视频暂停、电脑休眠时，按实际流逝的时间继续计时。
- 关闭全部哔哩哔哩标签页，或退出浏览器后，计时清零；下次打开从零开始。
- 暂时关闭跨刷新、关闭标签页和重启浏览器仍然有效，到期后再弹出；关闭期间可以延期。

扩展可以把这两类状态分开存放：

- 本次计时的起点放在 `chrome.storage.session`。浏览器进程还在时这块内存保留，扩展的服务工作线程被回收后也还在，因此刷新、页面在后台和电脑休眠都不会把计时清掉。退出浏览器，或在开发过程中重新加载扩展时，这块内存会被清掉，下次打开从零开始。
- 关闭标签页时用 `chrome.tabs` 查看是否还有哔哩哔哩标签页。最后一个哔哩哔哩标签页被关掉时清掉本次计时。刷新不会移除标签页，所以不会误清。这样即使用户只是关掉所有窗口、Chrome 仍在后台运行，计时也会清零。
- 暂时关闭的截止时间、目的与打断选项、历史记录和使用者设置放在 `chrome.storage.local`。它们在重启浏览器后仍然保留。到点唤醒使用 `chrome.alarms`，按设定的时刻提醒页面弹出询问，不把到时判断放在页面里容易被后台节流的定时器上。

篡改猴的 `GM_setValue` 写在磁盘上，浏览器退出后仍会留下。脚本也看不到浏览器里的标签页列表。页面卸载时无法区分刷新和关闭，电脑休眠时又不会发生卸载。因此脚本不能同时做到：休眠按实际时间继续计时、刷新后继续计时、关闭全部哔哩哔哩标签页或退出浏览器后清零。若用心跳把「一段时间没有页面上报」当成会话结束，休眠会被当成计时结束。

### 关闭当前标签页

打断窗口中的「关闭当前标签页」使用 `chrome.tabs.remove`，关闭用户自己打开的标签页，包括该窗口里只剩这一个标签页的情况。关闭动作写入记录；用户自己点浏览器的关闭按钮不写入记录。这一区分由按钮点击触发，不依赖监听标签页被关闭。

普通页面里的 `window.close()` 只能关闭由脚本打开的窗口。篡改猴可以通过 `// @grant window.close` 关闭当前标签页，但[其文档](https://www.tampermonkey.net/documentation.php?locale=en#window.close)写明：出于安全原因，不允许关闭一个窗口里的最后一个标签页。只开着一个哔哩哔哩标签页时，这个按钮不会生效。

### 其余条件如何满足

- 询问窗口和暂时关闭入口由内容脚本注入哔哩哔哩页面，视频播放页、搜索推荐页和主页都可以放置入口。
- 记录与设置保存在本机的 `chrome.storage.local`，不经过账号，也不上架。
- 哪些网址生效、默认时长、初始目的列表放在扩展内的站点配置中。以后增加网站时修改该配置，并按该站页面补上注入位置。
- 个人安装的代价是开启开发者模式并加载本地目录。Chrome 会提示当前启用了开发者模式扩展。重新加载扩展会清掉进行中的本次计时，已保存的记录和暂时关闭截止时间留在 `chrome.storage.local`。

### 不采用的做法

- **篡改猴脚本。** 可以注入页面，可以用 `GM_setValue` 保存记录，在窗口里还有其他标签页时也可以关闭当前标签页。它无法实现上面的计时生命周期，窗口里的最后一个标签页也关不掉，并且运行还依赖篡改猴这个额外扩展及其后续更新。
- **书签脚本。** 需要手动点击才运行，打开网站时不能自动询问，也没有跨标签页、跨休眠的共用计时。
- **本地代理，或放在浏览器外的拦截程序。** 需要处理 HTTPS 或另行保持一个进程，安装和维护超过个人使用所需，也做不到在页面里询问、填写备注并留下复盘记录。

数据字段、界面插在页面的哪个位置、闹钟如何对准使用者设置的分钟数，以及新增一个网站时要改哪些文件，写入后续的系统设计说明书。本节确定运行形态；迁入该说明书时沿用这里的结论。

## 7. 范围

**原文。** 当前只考虑哔哩哔哩网页。项目需要有扩展性，以后可以通过修改代码，对其他网站使用同一类限制。

**补充。** 当前要做的范围：

- 网页版哔哩哔哩上的目的询问、时长打断、暂时关闭、记录复盘。
- 个人在 Chrome 中安装使用。
- 把「哪个网站、何时询问、询问什么、如何计时」从页面细节里分开，使以后新增网站时主要改站点配置和必要的页面适配。

当前不做：

- 哔哩哔哩客户端、手机浏览器、其他桌面浏览器。
- 发布到 Chrome 网上应用店或篡改猴脚本市场。
- 账号登录、多设备同步、把记录发给他人。
- 自动屏蔽、隐藏或过滤短视频与推荐流。
- 在第一版里同时支持多个网站。扩展性只要求结构上留得出入口，不要求现在就接上第二个站点。



## 8. 开发方式

**原文。**

- 按软件工程规范，写代码之前先写完整的需求说明、系统设计等文档。
- 不一次性完成过多功能，分步逐条实现。

**补充。** 建议的文档和实现顺序：

1. **需求说明。** 把第 4 节里标出的待确认项写成可验收的规则，包括触发条件、计时规则、关闭规则、记录字段和异常情况（刷新、多标签、未作答）。
2. **系统设计。** 实现方式已在第 6 节选定。系统设计说明书说明数据存在哪里、页面如何注入界面、计时在何处运行，以及新增一个网站时要改哪些部分，并收入第 6 节的选型结论。
3. **分步实现。** 每一条都做完并确认可用，再做下一条。建议的切分是：
  - 先只在主页完成「目的询问 + 保存记录 + 查看记录」；
  - 再加入可配置的使用计时和打断；
  - 然后加入暂时关闭，并把关闭入口放到主要页面；
  - 最后整理站点适配方式，确认以后新增网站时的修改点。

每一步只增加一类可见行为，避免在目的询问还不稳定时同时改计时、关闭和多站点。

## 9. 留给需求说明确认的问题

下面这些会改变交互和计时行为，背景里先列出，不在这里做决定：

1. 「首次打开」按哪一种使用周期计算，刷新和多标签页会不会再次询问。
2. 直接打开视频、搜索或其他哔哩哔哩地址时，要不要做目的询问。
3. 使用时长是否只统计前台标签页，后台、暂停和休眠如何处理。
4. 时长打断时要回答到什么程度，以及回答后计时如何继续。
5. 暂时关闭的入口放在页面的什么位置，关闭期间目的询问是否仍然生效。
6. 目的列表的初始内容、如何新增和删除，以及已有历史记录里的旧目的如何显示。
7. 复盘入口放在扩展的哪个界面（例如浏览器工具栏上的弹出页，或扩展内的单独页面）。

需求说明应对每一条给出确定规则和对应的验收方式。
