# 报告：目的询问结束后页面点击没有响应

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-10-03 |
| 现象 | 目的询问里选择目的或跳过之后，哔哩哔哩页面上的点击没有响应。鼠标移到卡片上时，悬浮卡片仍会出现。从「暂停」进入暂时关闭之后，页面点击仍然没有响应。 |
| 结论 | 询问窗口已经卸掉，页面也已退出 `inert`。留下的是内容脚本挂在 `window` 上的捕获阶段监听。它在窗口关闭后继续拦截点击，而且不会卸下。暂时关闭没有另外加一层遮罩。 |

## 1. 现象对应的事件

悬浮卡片靠 `mouseover`、`mouseenter`、`mousemove` 这一类移动事件，或者靠 `:hover`。这些都不在拦截名单里，所以鼠标移过去时卡片仍会出来。

点击走的是 `pointerdown`、`mousedown`、`mouseup`、`click`。这些都在拦截名单里。事件在 `window` 的捕获阶段就被 `preventDefault()` 和 `stopPropagation()` 停住，到不了页面上的链接、按钮和脚本，所以看起来完全点不了。

「暂停」按钮在扩展自己的宿主节点里面。点击它时，事件路径包含这个宿主，拦截函数会直接放过。因此暂时关闭可以设上，但页面其余位置仍然点不了。这不是暂时关闭又挡了一次，而是询问结束时那组监听还在。

## 2. 拦截是怎么挂上的

`extension/src/content/ui.js` 的 `bindGuards` 只执行一次。询问窗口第一次挂上时调用它，时长打断窗口挂上时也会调用；第二次调用因为 `guardsBound` 已经为真而直接返回。

```142:160:extension/src/content/ui.js
function bindGuards() {
  if (guardsBound) {
    return;
  }
  guardsBound = true;
  ["click", "mousedown", "mouseup", "pointerdown", "pointerup", "auxclick", "contextmenu", "keydown", "keyup", "keypress"].forEach(function (type) {
    window.addEventListener(type, function (event) {
      if (!host || !host.isConnected) {
        return;
      }
      var path = typeof event.composedPath === "function" ? event.composedPath() : [];
      if (path.indexOf(host) !== -1) {
        return;
      }
      event.preventDefault();
      event.stopPropagation();
    }, true);
  });
}
```

监听加在 `window` 上，第三个参数 `true` 表示捕获阶段，早于页面自己的监听。条件不是「询问或打断还开着」，而是「宿主节点还连在文档上」。

宿主是 `[data-op-host="shell"]`，铺满视口，但自身是 `pointer-events: none`，不会靠盒子去接点击。目的询问、时长打断和「暂停」按钮共用这一个宿主。页面一加载，暂时关闭就会把宿主挂上，并一直留着，用来放右下角的按钮。询问结束时只去掉遮罩，不摘掉宿主。

因此 `host.isConnected` 在询问关掉之后仍为真。之后每一次不经过宿主的点击、按下和右键都会被吃掉。键盘的 `keydown`、`keyup`、`keypress` 同样会被吃掉。滚轮和鼠标移动不在名单里。

## 3. 关掉窗口时实际做了什么

确认或跳过成功后走 `closeInquiry`。它会恢复页面滚动、取消 `document.body.inert`、断开用来维持拦截的观察器，并删除 `.overlay`。它不移除 `bindGuards` 加上的监听，也没有把 `guardsBound` 设回假。

```623:633:extension/src/content/ui.js
function closeInquiry() {
  if (keepOnTop) {
    keepOnTop.disconnect();
    keepOnTop = null;
  }
  unblockPage();
  if (shadow) {
    var overlay = shadow.querySelector(".overlay");
    if (overlay && overlay.parentNode) {
      overlay.parentNode.removeChild(overlay);
    }
  }
```

`closeInterrupt` 同样只调用 `unblockPage` 并删除遮罩，不解除这组监听。

`unblockPage` 把 `blocked` 设为假，并执行 `document.body.inert = false`。询问关掉之后，挡住页面的不是 `inert`，也不是那层半透明遮罩。遮罩还在的话，鼠标会先碰到遮罩，页面上的悬浮卡片不会出现。现在悬浮卡片能出现，说明命中测试已经落到页面元素上，点击是在捕获阶段被脚本停掉的。

暂时关闭的 `applySnooze` 只更新按钮和位置，不调用 `blockPage` 或 `bindGuards`。从「暂停」设定分钟数，不会新加拦截；它也没有把已经加上的监听去掉。

## 4. 和已定行为的差别

询问或打断还显示着的时候，页面不能操作。这是需求 FR-1.7 和设计第 6.1 节要求的，这段拦截本身不该去掉。

询问确认或跳过、遮罩去掉之后，页面应当恢复点击。现在没有恢复。

时长打断点「关掉」之后的 5 秒里，需求 FR-2.10 要求该页可以操作。`closeInterrupt` 同样留下这组监听，这 5 秒里页面点击也会没有响应。再次弹出打断时，拦截继续生效，这一点与挡住页面的要求一致。

## 5. 建议的改法

监听可以留在 `window` 上，但只在询问或打断正在挡住页面时拦截。`blockPage` 已经把这个状态放在 `blocked` 里，`unblockPage` 会把它清掉。`bindGuards` 里的函数应先看 `blocked`：不为真就返回，不要用「宿主还在不在」当作条件。宿主会为了「暂停」按钮一直留在页面上。

不要在暂时关闭的路径上再加遮罩或 `inert`。那条路径现在没有挡点击，问题出在询问挂上、关闭时没有放开的那组监听。
